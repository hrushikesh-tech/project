# Plan 05-02: HR Module, Employee Lifecycle, Department Hierarchy, and Recursive Org Queries

<objective>
Implement the Phase 5 employee and department runtime slice: scaffold the NestJS HR module, expose tenant-safe employee and department APIs, enforce the locked lifecycle and department-head rules, and add recursive org-chart and department-tree query contracts with coverage.
</objective>

<must_haves>

- `apps/api/src/hr` exists as a vertical module wired into `AppModule`
- Employee endpoints support pre-start records, active-roster filtering, and future-dated terminations
- Department endpoints support parent-child hierarchy and optional same-department heads
- Org-chart reads use recursive CTEs and return correct depth values
- Department-tree reads remain separate from employee org-chart reads
- Raw recursive queries remain tenant-filtered at every step
- Unit and integration coverage prove lifecycle, department-head, and hierarchy behavior
  </must_haves>

<action>
Create `apps/api/src/hr/hr.service.ts` and implement the exact employee/department business rules below:

1. Employee creation:
   - allow creation before `hireDate`
   - set `status = 'PRE_START'` when `hireDate` is in the future
   - set `status = 'ACTIVE'` when `hireDate` is today or in the past and no termination is effective
2. Employee list/read behavior:
   - support an active-roster filter that returns only employees where `hireDate <= now`, `deletedAt is null`, and `terminationDate` is null or in the future
3. Employee update behavior:
   - allow scheduling `terminationDate` in the future without immediately removing the employee from active service
   - if the employee is already effectively terminated, reject changes to department, manager, hire date, and termination date while still allowing non-critical note/contact cleanup fields
4. Department create/update behavior:
   - validate that `headId`, when provided, references an employee in the same tenant
   - validate that the department head belongs to the same department
   - allow cross-department managers for employees; do not apply a same-department manager restriction
5. Reuse tenant-scoped Prisma delegates for all request-path reads and writes; do not use `prisma.raw` for normal lifecycle mutations.

Where lifecycle or validation rules fail, throw the shared HR exceptions created in plan `05-01`.
</action>

<action>
Add recursive hierarchy reads to `HrService` (or a dedicated helper under `apps/api/src/hr`) using parameterized raw SQL with these exact guarantees:

1. Employee org chart:
   - back `GET /api/v1/hr/org-chart`
   - support optional `rootEmployeeId`
   - use a recursive CTE over `Employee.managerId`
   - return at least `id`, `employeeCode`, `firstName`, `lastName`, `departmentId`, `managerId`, and `depth`
2. Department tree:
   - back `GET /api/v1/hr/departments/tree`
   - use a recursive CTE over `Department.parentId`
   - return at least `id`, `name`, `code`, `parentId`, `headId`, and `depth`
3. For both recursive queries, apply tenant filters in the anchor step and recursive step:
   - `tenantId = current tenant`
   - `deletedAt IS NULL`
4. Do not merge employee and department trees into one combined payload.

Keep the SQL in one clearly named location and keep all parameters bound rather than string-concatenated.
</action>

- Both recursive queries contain tenant filtering
- Both recursive queries contain `deletedAt IS NULL`
- The org-chart response path returns `depth`
- The department-tree response path returns `depth`
  </acceptance_criteria>

## Threat Model

<threat_model>

- **T-05-04: Unauthorized HR mutation** - Employee and department mutations must stay behind explicit HR/admin roles and tenant scoping.
- **T-05-05: Invalid hierarchy relationships** - Department heads must belong to their department, and lifecycle updates must not corrupt manager/department links after termination.
- **T-05-06: Recursive query tenant leak** - Raw recursive SQL can bypass Prisma tenant extensions unless tenant and soft-delete filters are embedded in every recursive step.
- **T-05-07: Roster leakage** - Pre-start and terminated employees must not appear in active-roster reads before or after their effective dates.
  </threat_model>
