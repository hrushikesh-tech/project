# Plan 08-03: NestJS Forecast Orchestration, Weekly Retraining, and ERP Persistence

<objective>
Create the NestJS side of Phase 8: aggregate tenant-safe demand history from inventory usage, call the FastAPI ML service, run weekly retraining, compare candidate versus active model quality, and persist promotions and forecast outputs in the ERP data model.
</objective>

<must_haves>

- NestJS has a dedicated forecasting module and ML service client
- Weekly retraining runs as a repeatable per-tenant job
- Demand history is aggregated from daily `ISSUE` inventory movements
- Promotion logic compares new versus active MAPE and only promotes improved models within the 20% gate
- Forecast metadata and outputs are persisted for later ERP use

</must_haves>

## Threat Model

<threat_model>

- **T-08-07: Cross-service drift** - Without one dedicated NestJS bridge, the ML service contract can sprawl across the codebase and become inconsistent.
- **T-08-08: Wrong demand series** - If the orchestration layer mixes receipts into the history or shifts to warehouse-level aggregation prematurely, the resulting forecasts will not reflect the locked phase decisions.
- **T-08-09: Unsafe promotion** - Without explicit compare-and-promote logic, weekly retraining could degrade the active model while still appearing successful.

</threat_model>
