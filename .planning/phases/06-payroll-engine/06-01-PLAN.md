# Plan 06-01: Payroll Schema Foundations, Blocking Prisma Sync, and Test Harness

<objective>
Create the payroll domain foundation required by every downstream Phase 6 task: persistent employee compensation structures, richer payroll-run state, immutable per-employee payroll results, shared payroll exceptions/contracts, and a dedicated payroll test harness. Finish with the mandatory Prisma sync before engine or queue work begins.
</objective>

<must_haves>

- Persistent employee payroll structure exists instead of ad hoc run-time gross-pay input
- Payroll data model supports employee-specific tax regime selection and effective-dated compensation changes
- Payroll runs are scoped to legal entity + pay period and can record retry/failure metadata
- Per-employee payroll results can be snapshotted before payslip generation and GL posting
- Shared payroll status/exception contracts are exported through `@amdox/types`
- A dedicated payroll harness can seed salary structures, payroll runs/results, payslips, tax slabs, and related HR/finance dependencies
- Prisma schema is pushed and regenerated before any downstream payroll module implementation
  </must_haves>

<task id="06-01-01" priority="high">
<description>Extend the Prisma payroll schema for compensation profiles, payroll run scope, employee-level result snapshots, and stronger payslip metadata</description>
<read_first>
- packages/db/prisma/schema.prisma
- .planning/phases/06-payroll-engine/06-CONTEXT.md

</read_first>
<action>
Update `packages/db/prisma/schema.prisma` with the exact payroll data-model changes below:

1. Extend `PayrollRun` so it is no longer just an aggregate counter shell:
   - add `legalEntityId String`
   - add explicit pay-period boundaries or equivalent normalized run-period fields
   - add optional failure/compensation metadata such as `failureReason`, `attemptNumber`, and `glJournalEntryId`
   - keep aggregate totals/counts and status timestamps
2. Extend `Payslip` so it carries a full immutable compensation snapshot:
   - keep `deductions Json` and `taxBreakdown Json`
   - add `earnings Json`
   - add fields needed to preserve S3 object location and rendered artifact metadata if `pdfUrl` alone is insufficient
3. Add a persistent employee compensation structure with effective dates. Use clear names such as `SalaryStructure` and `SalaryComponent`, or an equivalent normalized shape, with support for:
   - `employeeId`
   - effective-from / effective-to dates
   - employee tax regime (`OLD` / `NEW`)
   - recurring earnings components
   - recurring deduction components
   - flags or component typing for PF / professional-tax applicability and overtime eligibility
4. Add a per-employee payroll snapshot/result model such as `PayrollResult` linked to `PayrollRun` and `Employee`, storing:
   - gross pay
   - total deductions
   - net pay
   - earnings breakdown JSON
   - deductions breakdown JSON
   - tax breakdown JSON
   - payable-days / loss-of-pay / overtime-derived values
   - result status fields needed for retry-safe orchestration
5. Add the necessary tenant, employee, payroll-run, and legal-entity indexes for the new models.
6. Keep new payroll workflow states string-backed in application code rather than introducing new Prisma enums, consistent with the Phase 2 hybrid enum decision.

Do not remove or break the existing `PayrollRun`, `Payslip`, or `TaxSlab` models; evolve them into the full Phase 6 contract instead.
</action>

## Threat Model

<threat_model>

- **T-06-01: Compensation-model ambiguity** - Without a persistent employee compensation structure, execution will collapse into ad hoc run inputs and violate the locked Phase 6 context.
- **T-06-02: Schema/client drift** - If Prisma is not pushed and regenerated immediately after payroll schema changes, later plans can compile against stale generated types and fail at runtime.
- **T-06-03: Snapshot loss** - Without immutable per-employee payroll results, retries, payslips, and GL reconciliation will depend on recomputation instead of a stable run snapshot.
- **T-06-04: Harness blind spots** - Without a payroll harness that covers HR + finance dependencies, downstream tests will miss tenant scoping, tax, and compensation edge cases.
  </threat_model>
