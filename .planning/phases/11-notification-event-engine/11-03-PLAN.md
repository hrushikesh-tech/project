# Plan 11-03: Delivery Engine

## Objective

Implement the scheduled outbox poller, BullMQ delivery worker, event-catalog resolution, template rendering, and per-channel dispatch services that turn existing outbox rows into durable multi-channel notification delivery.

## Must-Haves

- Pending outbox events are claimed within the planned 5-second cadence.
- Delivery attempts transition through bounded retry logic with durable status updates.
- Event catalog drives recipients, channels, templates, and idempotent in-app behavior.
- Webhook delivery uses HMAC-SHA256 signing and timing-safe verification helpers.
- SMS is structurally supported but config-gated.

## Tasks

<task id="11-03-01" status="planned">

### Build the queue, processor, and 5-second outbox poller

Add:

- a notification queue registration
- a BullMQ processor
- a scheduled outbox poller service

The poller should select eligible pending rows, claim a bounded batch, and enqueue delivery work. The processor should manage retry transitions, next-attempt scheduling, and final terminal state updates.

</task>

<task id="11-03-02" status="planned">

### Implement event catalog, recipient resolution, and template fallback

Build the runtime catalog layer that defines for each supported event:

- channel support
- recipient resolution rules
- template-variable builders
- whether upstream code already created legacy in-app notifications

Use tenant override first and platform default second for templates, and ensure preference evaluation is default-on when no explicit row exists.

</task>

<task id="11-03-03" status="planned">

### Implement channel services for in-app, email, webhook, and SMS

Create the per-channel delivery services:

- in-app
- email
- webhook
- SMS

Webhook delivery must sign payloads using HMAC-SHA256 and use timing-safe verification helpers. SMS must remain config-gated so missing provider configuration yields a durable skipped or failed result rather than fake success.

</task>

<task id="11-03-04" status="planned">

### Add unit coverage for catalog and delivery semantics

Create unit tests for:

- catalog completeness for completed-phase events
- retry-state transitions
- template fallback behavior
- default-on preference filtering
- webhook HMAC signing helpers
- SMS config-gated skip behavior
- legacy in-app idempotency

</task>

## Threat Model

- Poller claim logic must avoid duplicate concurrent processing of the same outbox row.
- Recipient resolution must not leak tenant data or route events to the wrong users.
- Webhook signing must use constant-time comparison helpers for verification-related logic.
- Channel services must handle missing provider configuration without silently dropping durable evidence.

## Verification

- Unit tests cover catalog behavior, HMAC helpers, retry transitions, and SMS skip paths.
- App build includes the new queue and processor without module wiring regressions.
- Outbox rows move predictably through pending, retryable, delivered, failed, or skipped states.

## Success Criteria

- Wave 3 produces a working notification engine that can pick up committed outbox events and deliver them through the supported channels with durable retry and status behavior.
