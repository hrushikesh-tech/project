# Plan 11-02: Notification APIs

## Objective

Expose the Phase 11 API surface for inbox reads, mark-read actions, default-on user preferences, tenant template overrides, and tenant webhook configuration.

## Must-Haves

- Notification APIs register cleanly in the Nest application.
- Preference behavior is default-on even when no explicit row exists yet.
- Template resolution is tenant override first, platform default second.
- Webhook configuration is tenant-admin only and tenant-scoped.

## Tasks

<task id="11-02-01" status="planned">

### Register the notification module and API surface

Add a dedicated `notifications` module with:

- controller
- service
- DTOs
- exception filter
- serialization helpers

Register it in the application module using the repo's established backend module style.

</task>

<task id="11-02-02" status="planned">

### Implement inbox and preference APIs

Implement tenant-safe user-facing endpoints for:

- listing inbox notifications
- marking notifications as read
- reading effective preference state
- updating explicit notification preferences

The service logic must treat missing preference rows as enabled-by-default for supported channels and event types.

</task>

<task id="11-02-03" status="planned">

### Implement tenant template override and webhook config APIs

Add tenant-admin endpoints for:

- upserting notification template overrides
- reading effective template resolution
- creating and updating webhook configs
- activating, deactivating, and listing webhook configs

Webhook configuration should support broadcast delivery to all active endpoints that subscribe to the matching event.

</task>

<task id="11-02-04" status="planned">

### Add integration coverage for API and role-gate behavior

Cover:

- tenant scoping
- user versus admin permissions
- default-on preference behavior
- template fallback resolution
- webhook config CRUD behavior

These integration tests should become the guardrail for the configuration surfaces before the engine is wired in.

</task>

## Threat Model

- Tenant-admin APIs must not allow cross-tenant template or webhook config mutation.
- Preference endpoints must not let one user view or alter another user's inbox or preferences.
- Effective-template reads must not expose another tenant's overrides.

## Verification

- `notifications` module bootstraps in the app build.
- Integration tests prove role gates and tenant isolation.
- Default-on preference reads behave correctly with and without stored rows.
- Template and webhook config endpoints behave consistently across create, update, and read paths.

## Success Criteria

- Wave 2 leaves the phase with stable tenant-safe APIs that users and admins can configure before the delivery engine starts processing events.
