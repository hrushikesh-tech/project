# Plan 07-02: Supply-Chain Module, Purchasing Master Data, and Strict PO Lifecycle APIs

<objective>
Implement the Phase 7 request-path backend slice for purchasing setup and PO control: scaffold the NestJS supply-chain module, expose tenant-safe vendor/product/warehouse/replenishment APIs, and implement the PO creation/read/transition rules that enforce active-vendor usage, draft-only edits, and the rejection -> `DRAFT` loop.
</objective>

<must_haves>

- `apps/api/src/supply-chain` exists as a vertical module wired into `AppModule`
- Supply-chain writes require `supply_chain_manager` or `tenant_admin`
- Master-data APIs exist for vendors, products, warehouses, and replenishment settings
- PO create/read/transition APIs enforce the locked lifecycle rules
- New purchasing is blocked for `INACTIVE` and `BLACKLISTED` vendors
- Unit coverage proves rejection -> `DRAFT`, explicit send-to-vendor, and draft-only edit behavior
  </must_haves>

## Threat Model

<threat_model>

- **T-07-05: Soft purchasing controls** - If vendor status is treated as advisory instead of blocking, the system can create new POs against vendors that should not be purchasable.
- **T-07-06: Illegal status mutation** - If PO status can be changed through generic updates, the rejection loop and explicit send step will become bypassable.
- **T-07-07: Post-approval edit drift** - If material changes remain allowed after submission/approval, purchasing approval loses integrity.
- **T-07-08: Route-role mismatch** - If supply-chain routes do not follow the repo's explicit role decorator pattern, tenant or read/write access can drift from project expectations.
  </threat_model>
