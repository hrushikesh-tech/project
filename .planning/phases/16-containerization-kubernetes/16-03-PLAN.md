# Plan 16-03: Traffic Policies And GitOps Manifests

<objective>
Layer the Phase 16 rollout surface on top of the Helm chart by adding split-host ingress, API-only Istio canary resources, and an ArgoCD app-of-apps structure with deterministic sync ordering.
</objective>

<must_haves>

- ingress covers only the chart-owned public app surfaces
- the API can render stable/canary subsets with a `90/10` traffic split
- auth remains external to the chart and is consumed through config only
- ArgoCD manifests use a root app and environment child apps
- automated sync, self-heal, prune, and sync waves are explicit in GitOps manifests

</must_haves>

## Threat Model

<threat_model>

- **T-16-07: Traffic policy owns the wrong surface** - If ingress or canary resources try to own the external auth domain, the chart boundary is violated and rollout complexity leaks into an unmanaged dependency.
- **T-16-08: Misrouted canary traffic** - If stable/canary subsets are not explicit, the `90/10` split becomes ambiguous and hard to verify.
- **T-16-09: Out-of-order GitOps sync** - If ArgoCD applies traffic resources before shared config and workloads exist, first syncs can fail or converge unpredictably.

</threat_model>
