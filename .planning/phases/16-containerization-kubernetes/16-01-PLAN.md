# Plan 16-01: Runtime Packaging Foundations

<objective>
Create the container-ready foundation for Phase 16 by introducing `.dockerignore`, multi-stage Dockerfiles for all three shipped runtimes, and the API runtime split needed to separate public HTTP serving from background worker execution in Kubernetes.
</objective>

<must_haves>

- `api`, `web`, and `ml-service` each have a real multi-stage Docker build path
- the API runtime no longer depends on `nest start` as the final production container entrypoint
- the ML container binds to `0.0.0.0` and is cluster-reachable
- a dedicated API worker bootstrap exists so HTTP and background workloads can be scheduled separately
- the runtime/env contract is explicit before Helm chart work begins

</must_haves>

## Threat Model

<threat_model>

- **T-16-01: Dev-only entrypoints in production containers** - If runtime images depend on `nest start` or shell-driven wrappers, the API container will not meet the distroless/non-shell requirement cleanly.
- **T-16-02: Background execution coupled to public HTTP scale** - If processors and pollers remain bound to the API deployment, HPA on request traffic will accidentally scale asynchronous side effects.
- **T-16-03: Unreachable ML runtime** - If `uvicorn` stays bound to loopback, the service will appear built but be unreachable from the cluster.

</threat_model>
