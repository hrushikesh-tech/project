# Plan 09-01: BI Schema Foundations, Shared Contracts, and Test Harness

<objective>
Create the Phase 9 foundation required by every downstream BI task: evolve the existing dashboard schema for widget configuration and scheduled reporting, add shared BI-domain contracts, document the report-delivery environment surface, and create a reusable BI test harness. Finish with the Prisma/client sync before any API or metric implementation begins.
</objective>

<must_haves>

- Dashboards and widgets can persist the Phase 9 configuration surface without becoming a generic query builder
- The schema can represent scheduled reports and report-run artifact status durably
- Shared BI contracts and exceptions exist in `@amdox/types`
- BI report-delivery environment variables are explicit in `.env.example`
- A reusable BI test harness exists for dashboards, widgets, report schedules, report runs, and cross-domain metric fixtures
- Prisma/client sync happens before downstream BI implementation

</must_haves>

## Tasks

<task id="09-01-01" priority="high">
<description>Extend the BI Prisma schema for saved widget configuration, report schedules, and durable report-run artifacts</description>
<read_first>
- packages/db/prisma/schema.prisma
- .planning/phases/09-business-intelligence-dashboard/09-CONTEXT.md
- .planning/phases/09-business-intelligence-dashboard/09-RESEARCH.md
- .planning/REQUIREMENTS.md
</read_first>
<action>
Update `packages/db/prisma/schema.prisma` so the existing BI foundation can support the locked Phase 9 workflow. Make the exact schema changes below:

1. Evolve `Dashboard` and `Widget` so they can persist the saved BI contract, including:
   - dashboard ownership and tenant-internal visibility
   - widget title, type, metric key, layout/position JSON, and constrained config JSON
   - explicit timestamps and indexes that make dashboard-by-owner and widget-by-dashboard lookup efficient
2. Add a report schedule model tied to dashboards with support for:
   - dashboard linkage
   - schedule metadata
   - recipient metadata
   - enable/disable state
   - report format selection covering PDF and Excel
3. Add a durable report run / artifact model with support for:
   - schedule linkage
   - dashboard linkage
   - run status
   - started/completed timestamps
   - artifact key/URI metadata
   - delivery status or failure reason
4. Keep BI metric configuration JSON-backed rather than introducing a generic relational analytics-builder schema.
5. Preserve tenant scoping and soft-delete conventions on all new BI models.

Do not replace the existing `Dashboard` and `Widget` models with a disconnected reporting registry. Evolve the existing schema in place.
</action>

## Threat Model

<threat_model>

- **T-09-01: Underspecified BI persistence** - Without schedule/run/artifact models, BI-05 cannot be audited or retried cleanly.
- **T-09-02: Contract drift** - Without shared BI contracts, widget and metric validation will fragment across controllers and services.
- **T-09-03: Harness gap** - Without a BI-specific harness, downstream tests will duplicate brittle multi-domain setup and under-test tenant-safe metric behavior.

</threat_model>
