# Plan 04-01: Finance-Aware AP/AR Schema, Contracts & Test Harness

<objective>
Harden the shared AP/AR data model so invoice ingestion, three-way matching, ledger posting, mismatch notifications, and aging reports can be implemented against finance-safe, legal-entity-aware records. Establish shared enums/exceptions and a dedicated AP/AR test harness before queue or controller work begins.
</objective>

<must_haves>
- `Invoice`, `Vendor`, `PurchaseOrder`, and `GoodsReceipt` carry `legalEntityId`
- A first-class `Customer` model exists so receivable aging is implementable
- Invoice lifecycle fields support OCR queueing, review, and posted-ledger traceability
- Three-way match records store quantity, variance, review state, and mismatch reasons
- Shared AP/AR enums and exceptions exist in `@amdox/types`
- AP/AR test helpers can seed invoices, counterparties, PO/GR chains, outbox events, and notifications
- Counterparty posting configuration is explicit; missing control accounts route invoices to review rather than fallback posting
</must_haves>

## Threat Model

<threat_model>
- **Cross-entity misposting:** AP/AR records must carry `legalEntityId` so later auto-posting cannot write into the wrong books.
- **Receivables data gaps:** Without a `Customer` model, AR aging becomes ad-hoc and hard to secure. Introduce it before controllers or reports are written.
- **Status ambiguity:** Stringly-typed worker states cause duplicate processing and weak operator review. Shared enums make queue and review transitions explicit.
- **Test blind spots:** OCR, mismatch, and aging behaviors need dedicated state fixtures so later execution does not silently pass with finance-only coverage.
</threat_model>
